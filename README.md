## ⚛️ Core loop

Each chemical element is a level:

1. Fly around the atom using inertia-based movement.
2. Fire at the orbiting electrons until they detach.
3. Collect loose electrons as shop currency.
4. From **Beryllium onward**, fight against increasing nucleus gravity.
5. Clear every orbital electron and the nucleus destabilizes.
6. The core splits into collectible **blue neutrons** and dangerous **red protons**.
7. Win the post-core phase in either of two ways:
   - collect **every blue neutron** for an immediate finish; or
   - stay alive until the collection timer reaches zero.
8. Spend collected particles on ships, weapon upgrades, engines, and modules.
9. Continue all the way from **Hydrogen to element 118**.

Early atoms give a full **60 seconds** after the nucleus splits. Starting after Neon, the collection window gradually decreases until reaching the **20-second minimum** at element 118.

## 🔫 Weapons

Weapons are now actual upgrade families rather than unrelated one-off purchases.

| Family | Starter / Stage 1 | Stage 2 | Stage 3 | Stage 4 |
|---|---|---|---|---|
| **Blaster** | Blaster | Blaster 2000 | Blaster 3000 | Blaster 4000 |
| **Gatling** | Gatling Gun | Gatling Gun P | Gatling Gun S | — |
| **Burster** | Burster | Burster F | Burster R | — |

Notable progression details:

- The free starter **Blaster fires 1 projectile**, then the family upgrades through **2 → 3 → 4 projectiles** with Blaster 2000/3000/4000; Blaster 4000 shots can penetrate two electrons.
- Gatling progresses from **6 → 10 → 20 rounds/sec**. Gatling Gun S trades per-hit damage for extreme fire rate and therefore needs two hits per electron.
- Burster progresses from **5 → 7 → 10 projectiles** per burst with improved velocity, precision, and reload behavior.
- Every weapon has a finite **energy capacity** and **regeneration rate**. Holding FIRE forever is no longer free.
- Burster variants use deliberate trigger bursts rather than continuous automatic fire.

The ENERGY meter in the in-game top bar shows the current weapon reserve. The Ammo power-up restores it instantly.

## ♾️ Marathon

Marathon is now a continuous run instead of a chain of independently reset Classic levels.

- You begin with **3 ships**.
- Lives persist as you move from one element to the next.
- Score, run time, neutron count, and extra-life progression persist across the run.
- Extra ships are awarded at the same escalating threshold pattern used by the reference game:

```text
10,000
25,000
45,000
70,000
100,000
135,000
175,000
220,000
...
```

- The game announces the next extra-ship threshold.
- Leaving a Marathon from Pause saves the current run and the main menu offers **Marathon • Resume**.
- Finished/failed attempts are kept in **Records → Marathon history**.
- Results compare the current attempt with your previous best score and tell you how far ahead or behind you are.

## 🏆 Records

The new Records screen tracks more than a single high score.

For each element it stores:

- best score;
- best completion time;
- highest neutron collection count.

For Marathon it stores recent run history with:

- total points;
- farthest element / full completion;
- total run time;
- collected neutrons.

Existing 1.1.x high scores are migrated into this richer record format automatically.

## 🎮 Controls

### Desktop

| Action | Keyboard / Mouse |
|---|---|
| Turn / aim | `A` / `D`, `←` / `→`, or mouse while firing |
| Thrust | `W` / `↑` |
| Reverse thrust | `S` / `↓` |
| Fire | `Space` or left mouse button |
| Pause | `Esc` |

### Touch control modes

**Shoot + Fly&Aim** — one analog stick gently aims; pushing it past the configured dead zone also engages thrust. FIRE sits on the opposite side.

**Fly + Shoot + Aim** — separate flight and aim sticks with a dedicated FIRE button.

**D-pad** — directional thrust/turn controls plus a dedicated FIRE button.

The primary control side, analog size, and dead zone remain configurable. Control mode can also be cycled directly from the Pause menu.

## 📦 Windows + Android Releases

The Windows and Android workflows both run on `main`, version tags, or manual dispatch. They read the version from `package.json`; for this update that remains **`v1.2.0`**.

- `.github/workflows/windows.yml` builds and publishes **`Atom-Shooter.exe`**.
- `.github/workflows/android.yml` builds and publishes **`Atom-Shooter.apk`**.
- Both workflows use the same repository-wide release concurrency lock so they cannot edit the GitHub Release simultaneously.
- Each workflow replaces only its own platform asset. The Windows job never deletes the APK, and the Android job never deletes the EXE.
- Both workflows run the parity/regression suite before publishing.

Permanent latest-download URLs:

**Windows:** https://github.com/Draconov/Atom-Shooter/releases/latest/download/Atom-Shooter.exe  
**Android:** https://github.com/Draconov/Atom-Shooter/releases/latest/download/Atom-Shooter.apk

The Android project does not duplicate `web/`: Gradle packages the repository's canonical `web/` directory directly into the APK and serves it through AndroidX `WebViewAssetLoader`. ES modules, local storage, touch controls, Web Audio, and the existing responsive UI therefore use the same source as the browser build.

## ⚡ Performance

The game avoids unnecessary per-frame work by:

- pre-rendering the static arena background;
- caching electron-shell radii;
- tracking remaining electrons/neutrons directly rather than rescanning the scene for HUD values;
- updating DOM HUD content only when its visible state changes;
- bounding temporary VFX particles;
- skipping nucleus-particle simulation before the split;
- preloading game/shop art during the splash screen;
- using a single shared browser game implementation for GitHub Pages, Electron, and Android WebView rather than maintaining separate gameplay engines;
- pausing procedural music scheduling while the page is hidden.
